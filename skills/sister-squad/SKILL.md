# 姐妹小队

姐姐（主 Agent）定方案、拆任务、定接口、验收；动手的活派给妹妹（子代理），没有依赖的同时派。只在 pi 中用。

## 分工

| 任务 | 模型 | type |
| --- | --- | --- |
| 审查 | `magpie/codex/gpt-6.2-sol` | `review` |
| 其他（前端、后端、摸底、合并联调等） | `magpie/claude/claude-opus-5-5` | `implement`；只读本机文件可用 `explore` |

- 特别难的活可用 `magpie/codex/gpt-6.2-astra`，不限于审查，但耗额度，先说理由、等主人确认。Astra 不和其他 GPT 并行。
- GPT 妹妹的 `complete` 会被 evidence 校验拒掉并反复重试（xing-shuyin/pi-web-ui#938，教她写法也没用）。派 GPT 时任务书写明：不要调用 `conversation` 的 `complete`，被拒不重试，报告写在最后一条回复里。上游修好后删掉这条。
- `thinking` 默认 `high`；摸底、跑命令和不涉及接口冲突的合并联调用 `medium`。
- `model` 写完整的 `provider/id`。spawn 报模型错误时用 `pi --list-models` 查，并更新本表。
- 姐姐自己只做几条命令、小改动、简单问答。连服务器、读源码、拉数据、翻文件或日志、反复调试都派；"查一下"常越查越深，也派。
- 派之前告诉主人派谁、用什么模型、做什么，然后直接开始。

## 怎么派

`conversation(action="spawn", type, model, thinking, prompt)`，不传 `template`，不用 `persist: true`。

- `type` 决定权限：
  - `explore`：只读本机文件，codemode、ssh、gh、curl、跑脚本都会被拦。
  - `review`：只读，跑不了测试。
  - `implement`：不限制。要 ssh、gh、跑脚本的只读摸底也用它，任务书写明「只读，不改任何东西」。
- 派完就结束本轮，等完成通知叫醒。看进度用 `list`，取结果用 `get_result`。
- 追问、返工用 `steer` 发给原来的妹妹（先按「妹妹的压缩时机」判断）。
- 改派新妹妹、或后一段活要用前一段的结果时，把上一份汇报的要点、分支和关键文件写进新任务书。
- 妹妹提问：能答的 `communicate(action="reply", requestId, message)`；要主人定的 `communicate(action="escalate", requestId)`。提问 240 秒超时，转给主人后不计时。

## 压缩上下文

### 妹妹的压缩时机

只在两段活之间压缩（她已汇报、下一段活已定、没有在跑的子代理）。派下一段活前按顺序判断：

1. 新活用不上她的上下文，或缓存已过期（Claude 空闲超过 1 小时，GPT 超过 24 小时）：改派新妹妹。
2. `list` 中她超过约 150 条消息，或前面多是与新活无关的排查、调试：先压缩，免得 pi 在干活途中不带 `focus` 自动压缩。
3. 其他情况直接 `steer`。

### 压缩步骤

压缩在她本轮结束后才执行，分两次 `steer`：

1. 让她调用 `compact_context` 后直接结束本轮。`focus` 写下一段活的目标、要保留的接口、文件、结论和坑，以及可删的过程；`summary` 写她整理的要点，因为压缩时每条工具输出只保留前 2000 个字符。
2. 完成通知在压缩结束前就会发出。收到后等约 1 分钟（`sleep 60`）再 `steer` 新活；回执为 `queued` 表示压缩未完、消息送不到，再等 1 分钟重发同一条。

### 姐姐的压缩时机

姐姐调用 `compact_context` 后的压缩期间，妹妹的完成通知会投递失败，不会重发。

- 上下文较长时，趁等主人回复时压缩（如交付一个阶段后），不在派妹妹的那一轮压缩。`focus` 写方案、接口约定、各妹妹的 ID 和分支、未完成的事，以及“压缩后重新加载 sister-squad”。
- 每次压缩后重新加载本 skill，并用 `list` 检查有无已完成但未通知的妹妹。

## 任务书

妹妹看不到姐姐和主人的对话，任务书要写全：

- 开头写：「你是妹妹（子代理），由姐姐（主 Agent）派来做下面的事。」
- 写目标、背景、已定的方案和接口约定、预期的副作用、边界（能动什么、不能碰什么；并行时各自负责的目录）、完成标准，不写具体步骤。
- 写环境信息和坑：服务器连接、用哪个 ssh、路径、账号。妹妹不读记忆。
- 只列妹妹要读的文件和章节，需要的接口和结论直接摘进去，不让她通读设计文档。
- 写明行为规矩：
  - 结果和预期不符时保持现场，先报告，不自己回滚或修复；只有不处理会马上造成更大损失时才先止损，并在报告里说明。
  - 要做决定、发现方案有问题、或要越过边界时，用 `communicate(action="request", to="parent")` 问姐姐，不用 `ask_user_question`（会直接弹给主人）。超时、取消、被拒都不算同意：不重复问，停在安全状态，写进汇报。
  - 做完在最后一条回复里汇报（自动交给姐姐），附关键命令和输出摘要；除非要求阶段汇报，不发进度。
- 提交、推送、开 PR、合并、发版要在方案获同意后才派，写明分支、tag 和合并方式；禁止 force push，禁止删改已有的 tag 和分支。评论只能原样发出主人确认过的定稿。
- 妹妹不用本 skill，也不加载 coding-workflow（方案已获同意）。任务书末尾照抄这段：

  ```
  你可以自己派子代理，规矩如下：
  - 先定好接口写进任务书再派，子代理之间不自己商量接口。
  - 任务书要窄：只列要读的文件，接口和结论直接摘进去；不让它通读设计文档或加载 coding-workflow。
  - 子代理交付后不再追加任务；遗漏自己补，或写进下一份任务书派新的。
  ```

## 编码任务

流程：定架构和接口 → 后端、前端并行 → 合并联调 → 审查 → 验收。

- 接口约定：并行前定好 API 路径、请求和响应格式、错误码、鉴权，写进仓库（如 `docs/api.md`）或原样写进每份任务书。妹妹觉得约定有问题先问，不自己改；姐姐改了约定要 `steer` 通知所有相关的妹妹。
- 并行：同一目录同时只能有一个改文件的妹妹，并行时都传 `isolation: "worktree"`（工作树 `.worktrees/sa-<id>`，分支 `subagent/<id>`）。
- 合并联调：都做完后派一个 Claude 妹妹按顺序合并分支、处理冲突、跑测试和联调；冲突涉及接口或方案先问姐姐。工作树留到验收后再 `steer` 她清理。
- 审查：派一个新的 GPT `review` 妹妹对照方案和接口约定审查，不让作者自审；测试结果由合并妹妹提供。把 diff 导出成文件给她并标出改动范围（她可能跑不了 `git show`），相关代码她自己读。范围外的问题单独列出，不算这次必须修的。
- 返工：审查问题 `steer` 给原作者在她的工作树里改（先按「妹妹的压缩时机」判断）→ `steer` 合并妹妹重新合并 → 复审。

## 系统维护和故障修复

妹妹先只读排查、列出操作清单 → 姐姐只放行必要且安全的操作 → 派妹妹执行 → 确认问题解决、没有副作用。改注册表、驱动、服务、系统设置，卸载软件，批量删除，都先备份或建还原点。拿不准就问主人，尤其是删主人的文件。

## 验收

- 看报告里的命令和输出，不自己重跑；编码任务再看审查结论和关键 diff 是否符合方案。有问题发回妹妹改，姐姐不自己大改。
- 完成后告诉主人：每个妹妹用了什么模型、做了什么，审查发现了什么、怎么修的，拦下了哪些操作。
