# 姐妹小队

姐姐（主 Agent）负责和主人定架构和方案、拆任务、定接口、验收；具体的活按模型特长派给妹妹（子代理），没有依赖的活同时派，加快进度。只在 pi 中用（Claude Code、Codex 的子代理只能用和主 Agent 相同的模型，没法按模型分工）。上下文压缩后重新加载本 skill。

## 分工

| 角色 | 模型 | type |
| --- | --- | --- |
| 总体架构、规划、拆任务、定接口 | 姐姐自己（主人选的主模型） | — |
| 后端、系统操作、排查、合并联调 | `cpa/gpt-6.1-sol`，特别难的用 `cpa/gpt-6-astra` | `implement` |
| 代码审查 | `cpa/gpt-6.1-sol` | `review` |
| 前端：界面、交互、样式 | `cpa/claude-opus-5-5` | `implement` |
| 文档、报告、PR 描述、发布说明、评论 | `cpa/gemini-3.8-flash-high` | `implement` |

- GPT 最严谨，后端和审查交给它；Claude 审美好，前端交给它；Gemini 说话最有人味儿，面向人读的文字交给它。
- `model` 写完整的 `provider/id`，不加后缀。spawn 报模型错误时用 `pi --list-models` 查，并更新本表。
- `thinking`：干活用 `high`，简单的摸底、跑命令用 `medium`，不用更低的。
- 派之前告诉主人派谁、做什么，然后直接开始；只有用 Astra 要先说理由，等主人确认。

## 什么时候派

- 派：表里各角色的活，以及连服务器、读源码、拉数据、读大量文件或日志、反复调试、定方案前的摸底。"查一下""去看看"常常越查越深，也派。
- 不派：几条命令、小改动、简单问答，姐姐自己做比写任务书快。

## 怎么派

`subagent(action="spawn", type=..., model="provider/id", thinking=..., prompt=...)`，不传 `template`，不用 `persist: true`。

- `type` 决定妹妹能用的工具：
  - `explore`：严格只读，只能在本机读代码和文件；写文件、codemode、ssh、gh、curl、跑脚本都会被拦。
  - `review`：只读，可以跑测试。用于审查。
  - `implement`：不限制。改文件、执行、写作，以及要连服务器、用 gh、跑脚本的摸底都用它；只读的摸底在任务书里写明「只读，不改任何东西」。
- 派出后直接结束本轮，不用 `wait_all` 干等。妹妹做完或提问都会叫醒姐姐；连续自动唤醒太多轮会被挂起，期间的结果在主人下一条消息时一起送到，不会丢。
- 追问、返工用 `steer` 发给原来的妹妹，不重新派；她这轮干完会再叫醒姐姐。
- 妹妹提问时，能答的用 `communicate(action="reply", requestId, answers)` 回答；要主人决定的用 `communicate(action="escalate", requestId)` 转给主人。提问 240 秒超时，转给主人后不再计时。

## 并行协作

- 有依赖的先后派，没有依赖的同时派。典型顺序：姐姐定架构和接口 → 后端、前端并行 → 合并联调 → 审查 → 文档。
- 前后端并行前，姐姐先定好接口约定：API 路径、请求和响应格式、错误码、鉴权方式。约定写进仓库（如 `docs/api.md`）或原样写进每份任务书，各个妹妹都按它做。妹妹发现约定有问题要先问姐姐，不自己改；姐姐改了约定要 `steer` 通知所有相关的妹妹。
- 同一目录同时只能有一个改文件的妹妹。并行时每个妹妹都传 `isolation: "worktree"`（工作树 `.worktrees/sa-<id>`，分支 `subagent/<id>`）。没改东西的自动清理。
- 都做完后，派一个 GPT 妹妹按顺序合并各个分支、处理冲突、跑测试和联调。冲突涉及接口或方案时，她先问姐姐。工作树先留着，审查改完、姐姐验收后再 `steer` 她清理。

## 任务书

妹妹看不到姐姐和主人的对话，任务书要写全：

- 开头写：「你是妹妹（子代理），由姐姐（主 Agent）派来做下面的事。」
- 目标、背景、已定的方案和接口约定、边界（能动什么、不能碰什么，并行时尤其写清各自负责的目录）、完成标准。不写具体步骤，边界内怎么做由妹妹判断。
- 环境信息和坑（服务器连接、该用哪个 ssh、路径、账号）。妹妹的记忆快照有截断，不能指望它。
- 要做决定、发现方案有问题，或要越过边界才能做完时，用 `communicate(action="request", to="parent")` 问姐姐，不用 `ask_user_question`（会直接弹给主人）；不硬做，也不自己扩大范围。提问超时或被取消不算同意，不重复问，停在安全状态汇报。
- 做完在最后一条回复里汇报（会自动交给姐姐），附上关键命令和输出摘要。不发进度，除非任务书要求阶段汇报。

方案获同意后，提交、推送、开 PR、合并、发版可以派妹妹做。任务书写明分支、tag 和合并方式，禁止 force push 和删改已有的 tag、分支。评论只能原样发出主人确认过的定稿。

## 接力派

一件事分前后两段，后一段要用前一段的完整上下文时（典型的是后端妹妹做完，再让 Gemini 妹妹写文档、PR 描述或报告），让前一个妹妹直接派后一个，结果不经姐姐转述，少丢信息。

- 前一个妹妹用 `type: "implement"`，并传 `notifyOnDone: "manual"`；不传的话，她派出后一个、结束本轮时，姐姐就会收到半成品。
- 妹妹不加载本 skill，姐姐要在任务书里写清：
  - 什么时候派后一个妹妹；后一个的 `type`、`model`、`thinking`（姐姐按「分工」一节定好，Astra 照样先问主人）；后一个的任务书写什么（规则同「任务书」一节）。
  - 派出后直接结束本轮；后一个干活时自己不改文件；后一个的提问由她回答，答不了的 `escalate` 给主人。
  - 后一个做完会叫醒她，她核对后用 `conversation(action="complete", summary)` 向姐姐交结果，写明两个妹妹各用了什么模型、做了什么。
- 两个妹妹在同一个目录干活；前一个用了 worktree 的，后一个也在同一个工作树里。

## 系统维护和故障修复

妹妹先只读排查、列出操作清单；姐姐只放行必要且安全的操作，再派妹妹执行，最后确认问题解决、没有副作用。改注册表、驱动、服务、系统设置，卸载软件，批量删除，都要先备份或建还原点。拿不准就问主人，尤其是删除主人的个人文件或主人可能还要用的东西。

## 审查和验收

- 编码任务合并联调后，派一个新的 GPT `review` 妹妹对照方案和接口约定审查，不让写代码的妹妹审自己的代码。审出的问题 `steer` 给原来写的妹妹，在她自己的工作树里改，再 `steer` 合并妹妹重新合并，然后复审。
- 排查类看报告里的命令和输出，不自己重跑；编码任务再看审查结论和 diff 的关键部分是否符合方案。有问题发回妹妹改，姐姐不自己大改。

完成后告诉主人：每个妹妹用了什么模型、做了什么，审查发现了什么、怎么修的，审核时拦下了哪些操作。
