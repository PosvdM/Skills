# 项目文档

在编码任务中维护 README 和技术文档。人类开发者和 Agent 都会查阅这两类文档，因此它们遵守同一套写作规范。

## 何时更新文档

每次修改代码后、结束任务前，检查改动是否影响以下内容：

- 使用者可见的功能、行为、默认值和限制
- 安装步骤、配置项、命令、环境要求和依赖
- 文件结构、模块职责、接口和数据格式
- 文档中的示例、截图说明和链接

在对应位置修改受影响的内容，删除失效的内容；不在文档末尾追加“更新记录”或“本次修改”。改动不影响文档时不改。

写入前对照代码核实命令、路径、默认值和配置名。未实现的功能不写成已有功能；无法核实的内容向用户确认。

在回复中列出更新了哪些文档；没有更新时，用一句话说明原因。

## README 与技术文档的分工

README 写给使用者和第一次接触项目的人：

- 项目做什么、主要功能
- 安装、配置和使用方法
- 使用者能观察到的行为、默认值和限制
- 开发入口：环境要求、常用的构建和测试命令、技术文档链接

技术文档写给修改代码的人：

- 架构、模块职责和数据流
- 源码路径、常量、配置项、存储格式、接口和协议
- 构建、测试和发布流程
- 仍然有效的设计约束及其原因
- 修改代码时要遵守的约定，如“修改 A 后需同步更新 B”

只有修改代码的人才需要的信息放进技术文档。README 涉及实现细节时，用一句话说明并链接到技术文档。两类文档都面向所有读者；只给 Agent 的指令放在 `AGENTS.md` 等文件中。

组织方式：

- 沿用项目已有的文档目录和文件名。没有时使用 `docs/`，按主题分文件，如 `docs/architecture.md`、`docs/development.md`。
- 技术细节较少时，一个文件即可。没有内容可写时不建文档目录，也不建空模板。
- 同一信息只在一处完整说明，其他位置链接过去。
- README 有其他语言版本（如 `README_EN.md`）时，同步更新各版本。

## 只写当前状态

README、技术文档和代码注释说明项目现在怎样工作、怎样使用、为什么这样设计。变更经过写进提交信息、PR 描述、CHANGELOG 或发布说明。

- 不写“之前用 X，发现有问题，现在改为 Y”，直接写 Y。如果 X 的问题对后来的开发者有用，把它写成当前的约束。
- 代码改变后，在原位置改写或删除对应内容，不保留旧说明再追加新说明。
- “现在”“已改为”“不再”“新增”“修复”等词常用于描述版本变化，出现时检查是否在讲变更经过。描述操作前后的状态（如“关闭后不再自动添加”）可以使用。
- 例外：使用者需要据此操作的升级说明可以保留，写明适用版本和操作步骤；不再需要照顾这些旧版本时删除。

示例：

- 改前：“我们最初用 `localStorage` 保存设置，但后台脚本无法访问它，现在改用 `chrome.storage.local`。”
- 改后：“设置保存在 `chrome.storage.local`。后台脚本无法访问 `localStorage`，因此不使用它。”

## 整理杂乱的内容

更新文档时通读所修改的文件，发现以下问题时主动整理：

- 同一内容重复出现，或前后矛盾
- 内容与代码不符，或描述已删除的功能
- 包含变更经过
- README 中混有实现细节
- 同一主题分散在多个章节
- 套话、铺垫、重复的总结，以及其他不符合“写作规范”一节的写法

整理时删除重复和过时的内容，把实现细节移到技术文档，把分散的信息合并到一处。只删重复、过时和没有信息量的文字，不删仍然准确且有用的信息；无法确定是否过时，先核对代码或询问用户。组织清楚的部分保留原有结构，不为换风格重写，只逐句改写不合规范的句子。移动或删除较多内容时，在回复中说明。

## 写作规范

结构：

- 按主题设标题，段落简短；并列信息用列表或表格。
- 标题用简短的名词短语点明主题，如“参数来源”，不写成“参数从哪里来”这样的口语问句。读者靠标题扫读和定位，标题也会出现在目录和锚点链接里。
- 写完整的句子，交代条件和原因。不写成关键词堆砌、电报体、任务日志或只有 Agent 能看懂的笔记。

用词：

- 删去不提供信息的修饰语：“文件已成功保存”可改为“文件已保存”；“强大灵活的配置系统”应改为说明能配置什么。保留影响否定、时间、频率、范围、程度、条件、可能性和结果的限定，如“暂时不可用”“仅支持 Windows”。
- 用事实替代评价：有数据时写“启动时间从 4 秒缩短到 2 秒”，不写“大幅提升启动速度”；没有数据时不编造。
- 直接写重点，用具体的名词和准确的动词，如用“分析日志”替代“开展日志分析工作”。省去铺垫、自问自答、总结标签和自造术语。
- 用书面语。文档会被反复查阅和转引，口语化的表述显得松散，意思也容易含糊。例如写“如需……”，不写“……的话”；写“运行中的 pi”，不写“已开着的 pi”；“弄”“搞”换成“迁移”“恢复”等具体的动词；“这段时间”换成明确的时间范围。书面语也不是公文腔，“予以”“进行……操作”这类空洞的说法同样不用。
- 避免“不是 A，而是 B”和 “X, not Y” 等对比句式，除非要纠正读者可能有的误解。
- 提到界面上的按钮、标签和栏目时，用界面上的原文，读者才能和界面对上。
- 标识符、命令、路径、配置键和代码保持原样，用代码格式标出；机器读取的格式按其语法书写。

## 其他文字

代码注释、提交信息、PR 标题和描述、发布说明以及界面文案同样遵守“写作规范”一节，并沿用项目已有的语言和格式约定。这些文字通常写完就直接发布，发布前对照“写作规范”一节通读一遍。

- 代码注释说明代码做什么、为什么这样做，不记录修改经过。
- 提交信息、PR 描述和发布说明记录改了什么、为什么改；需要时写出原来的行为。
- 界面文案（按钮、提示、悬停说明、报错信息）要简短：说清结果和使用者需要做的操作即可，原因和背景写进文档。例如“已取消 pi 默认模型，运行中的 pi 需执行 /reload”。
- 只修改与任务相关的注释和文案。

## 交接文档

工作要中断、之后再继续时，写一份交接文档，记录下一步要做什么。常见的情况：额度用完要等冷却、用户要休息、要换设备、上下文太长要开新对话，或者交给别的 Agent 接手。

- 放在仓库的 `docs/handoff/<主题>.md`，标题注明日期。
- 交接文档写给接手的人和 Agent，可以写指令，不受“只写当前状态”和“只给 Agent 的指令放在 `AGENTS.md`”两条限制。
- 写清：方案是否已获用户同意、能否直接开工和发版；进度，以及交接时 main 所在的提交；要做的事（用户要什么、做法、涉及的文件）；交付和发版步骤；需要注意的问题和尚未处理的问题。
- 接手的人看不到之前的对话，文档要能独立读懂。引用本机路径时注明是哪台机器。
- 不写密钥、token 和客户端 key。公开仓库只写脱敏的内容：不写服务器名、地址、账号、内部路径和备份位置，用“测试服务器”之类的泛称；部署和运维细节由用户另行提供。
- 工作完成后，在收尾的提交或 PR 里删除交接文档，需要时到 git 历史里查。
