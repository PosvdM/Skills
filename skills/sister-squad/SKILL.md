# 姐妹小队

我的主 Agent 额度紧张，所以分工如下：主 Agent 是大姐，负责理解需求、定方案、写任务书、审核和验收；复杂、耗额度的活交给子代理去做。

本 skill 只在 pi 中使用，判断依据是有 pi-subagents 提供的 `subagent` 工具。在 Claude Code、Codex 等其他 Agent 中不使用本 skill，也不要用它们自带的子代理工具（如 Claude Code 的 Agent/Task 工具）代替，照常工作即可：那些子代理用的仍是同一家的模型，省不了额度。

## 什么时候派子代理

默认主 Agent 自己做。下面这类复杂、耗额度的活才派出去：

- 要读大量文件或日志，或者要大范围扫描（如代码库摸底、磁盘占用、系统日志）
- 要改多个文件，或者要反复跑测试、反复调试
- 排查路线长，需要多次尝试
- 篇幅较长的写作

几条命令能完成的事、一两行的小改动、简单问答，主 Agent 直接做。派一次子代理的开销往往比直接做还大。

## 模型

每次派子代理都要在 `model` 参数里写明模型，用哪个模型都要写，包括 Claude。

| 用途 | 模型 |
| --- | --- |
| 常规执行：编码、系统操作、排查 | `cpa/gpt-6.1-sol` |
| 特别难的任务 | `cpa/gpt-6-astra`。很耗额度，用之前说明理由 |
| 写作：文章、报告、PR 描述、发布说明、PR 和 issue 评论 | CPA 里最新的 Gemini 模型（写这份 skill 时是 `cpa/gemini-3.8-flash-high`） |
| 确实需要 Claude 的任务 | `cpa/claude-opus-5-5`，用之前说明理由 |

写作用的 Gemini 一律用最新版本。派出前查一下 `~/.pi/agent/endpoints.json` 里 `cpa` 服务的 `enabled` 列表，有更新的 Gemini 就用新的。

## 派工计划

派出子代理之前先列派工计划：每个子代理的角色、模型、任务，以及选这个模型的理由。

- 编码任务：派工计划写进 coding-workflow 要求的方案里，我同意方案就是同意派工。
- 非编码任务：用 `cpa/gpt-6.1-sol` 或 Gemini 时，说一声就直接开始；用 `cpa/gpt-6-astra` 或 Claude 时，先等我确认。

执行中要追加子代理或者换模型，也按这个规则处理。

## 角色

- `scout`：只读的摸底和排查，交回结论、证据和相关位置。
- `worker`：修改文件、执行命令、跑测试和构建、写作。同一个目录同一时间只派一个 `worker`。任务能拆成互不重叠的几块时，分块派出或者依次派。
- `reviewer`：coding-workflow 要求的 PR 审查由它来做。

## 编码任务

流程完全按 coding-workflow，本 skill 不改其中任何规则。子代理改文件也算"修改文件"，必须等我明确同意方案后才能派出。只读的子代理随时可以派。

## 非编码任务：大姐替我审核

系统维护、故障排查修复这类任务，由主 Agent 替我审核子代理的行为，不用我逐条批准：

1. 子代理先只读排查，交回发现和建议的操作清单，不要直接动手。
2. 主 Agent 逐条审核清单，只放行必要、安全的操作。
3. 派子代理只执行放行的操作。高风险操作（修改注册表、驱动、服务、系统设置，卸载软件，批量删除）在任务书里要求先备份或者先建系统还原点。
4. 执行完主 Agent 检查结果，确认问题解决、没有副作用。

主 Agent 判断不了的事要先问我。例如删除我的个人文件（文档、照片、项目、下载的资料），或者某样东西我可能还要用。

## 写作任务

子代理默认读不到我装的 skill，任务书里要给出 skill 文件的路径，让它先读全文再写：

- 文章、报告、邮件等：`~/.agents/skills/plain-language/SKILL.md`
- README、技术文档、PR 描述、发布说明：`~/.agents/skills/project-docs/SKILL.md`

对外发出的文字是否先给我看，按 coding-workflow 的规定。

## 任务书

每份任务书都写清：

- 目标和背景，已确定的方案
- 工作目录、可以改动的范围、不能碰的范围
- 约束：沿用的风格，不允许做的事
- 验收标准，以及怎么验证（要跑的命令）
- 遇到哪些情况必须停下来问，不能自己拍板
- 报告格式：做了什么、改了哪些文件或系统设置、验证结果、遗留风险

子代理不做提交、推送、开 PR、发评论这类对外操作，这些由主 Agent 按 coding-workflow 完成。

## 执行中的问题

子代理的问题在已同意方案的范围内，主 Agent 直接回答；超出范围的，先问我。

## 验收

主 Agent 看子代理的报告，编码任务还要看 `git diff --stat` 和关键改动，确认符合方案和验收标准。有问题就把具体问题发回给子代理修改，主 Agent 不自己大改。

完成后告诉我：每个子代理用了什么模型、做了什么，审核时拦下了哪些操作。
