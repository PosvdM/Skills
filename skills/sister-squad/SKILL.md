# 姐妹小队

姐姐（主 Agent）定方案、拆任务、定接口、验收；动手的活派给妹妹（子代理），没有依赖的同时派。只在 pi 中用。主人没要求、自己加载时，只派这次要派的活，不把整段对话改成派活模式。

## 分工

| 任务 | 模型 | type |
| --- | --- | --- |
| 审查 | `magpie/codex/gpt-6.2-sol` | `review` |
| 第二审查 | `magpie/agy-cli/gemini-4-neon` | `review` |
| 其他（前端、后端、摸底、合并联调等） | `magpie/claude/claude-opus-5-5` | `implement`；只读本机文件可用 `explore` |

- 特别难的活可用 `magpie/codex/gpt-6.2-astra`，不限于审查，但耗额度，先说理由、等主人确认。Astra 不和其他 GPT 并行。
- `thinking` 默认 `high`；摸底、跑命令和不涉及接口冲突的合并联调用 `medium`。
- `model` 写完整的 `provider/id`。spawn 报模型错误时用 `pi --list-models` 查，并更新本表。
- 姐姐自己只做几条命令、小改动、简单问答；连服务器、读源码、拉数据、翻文件或日志、反复调试都派，常越查越深的"查一下"也派。
- 派之前告诉主人派谁、用什么模型、做什么，然后直接开始。

## 怎么派

`conversation(action="spawn", type, model, thinking, prompt)`，不传 `template`，不用 `persist: true`。

- `type` 决定权限：
  - `explore`：只读本机文件，codemode、ssh、gh、curl、跑脚本都会被拦。
  - `review`：只读，跑不了测试。
  - `implement`：不限制。要 ssh、gh、跑脚本的只读摸底也用它，任务书写明「只读，不改任何东西」。
- 派完按预计完成时间用 `schedule` 定一个兜底唤醒，再结束本轮。最长 58 分钟（`in 58m`），超过 1 小时姐姐的缓存就过期了；定新的前先取消没触发的。完成通知可能丢，每次醒来都用 `list` 和 `get_result` 核对每个妹妹。
- 追问、返工用 `steer` 发给原来的妹妹（先按「妹妹的压缩时机」判断）。她交付约 15 分钟后可能被回收，steer 报找不到时改派新妹妹。
- 改派新妹妹、或后一段活要用前一段的结果时，把原任务书、上一份汇报的要点、各轮问题清单、分支和关键文件写进新任务书。
- 妹妹请示：能答的 `communicate(action="reply", requestId, message)`，报 "Unknown or settled request" 时改用 `steer` 送答复；要主人定的 `communicate(action="escalate", requestId)`。

## 压缩上下文

### 妹妹的压缩时机

只在两段活之间压缩（她已汇报、下一段活已定、没有在跑的子代理）。派下一段活前按顺序判断：

1. 新活用不上她的上下文，或缓存已过期（Claude 空闲超过 1 小时，GPT 超过 24 小时）：改派新妹妹。
2. `list` 中她超过约 150 条消息，或前面多是与新活无关的排查、调试：先按同目录 `compaction.md` 压缩，免得 pi 在干活途中不带 `focus` 自动压缩。
3. 其他情况直接 `steer`。

### 姐姐的压缩时机

姐姐压缩期间，妹妹的完成通知会丢。

- 上下文较长时，趁等主人回复时压缩（如交付一个阶段后），不在派妹妹的那一轮。`focus` 写方案、接口约定、各妹妹的 ID 和分支、未完成的事，以及“压缩后重新加载 sister-squad”。
- 每次压缩后重新加载本 skill（在做编码任务时连同 `coding.md` 一起重读），并核对各妹妹的状态。

## 任务书

妹妹看不到姐姐和主人的对话，任务书要写全：

- 开头写：「你是妹妹（子代理），由姐姐（主 Agent）派来做下面的事。」
- 写目标、背景、已定的方案和接口约定、预期的副作用、边界（能动和不能碰的；并行时各自负责的目录）、完成标准，不写具体步骤。
- 写环境信息和坑：服务器连接、用哪个 ssh、路径、账号。妹妹不读记忆。
- 只列妹妹要读的文件和章节，需要的接口和结论直接摘进去，不让她通读设计文档。
- 写明行为规矩：
  - 结果和预期不符时保持现场，先报告，不自己回滚或修复；只有不处理会马上造成更大损失时才先止损，并在报告里说明。
  - 要做决定、发现方案有问题或要越界时，用 `communicate(action="request", to="parent", timeoutSeconds: 1800)` 问姐姐，不用 `ask_user_question`（会直接弹给主人）。超时、取消、被拒都不算同意：不重复问，停在安全状态，写进汇报。
  - 做完在最后一条回复里汇报（自动交给姐姐），附关键命令和输出摘要；除非要求阶段汇报，不发进度。
- 提交、推送、开 PR、合并、发版要在方案获同意后才派，写明分支、tag 和合并方式；禁止 force push 和删改已有的 tag、分支。评论只能原样发出主人确认过的定稿。
- 妹妹不用本 skill，也不加载 coding-workflow（方案已获同意）。任务书末尾照抄这段：

  ```
  你可以自己派子代理，规矩如下：
  - 先定好接口写进任务书再派，子代理之间不自己商量接口。
  - 任务书要窄：只列要读的文件，接口和结论直接摘进去，不让它通读设计文档。
  - 追加任务只发给交付不到 1 小时（GPT 24 小时）、新活要用它的上下文、消息不到约 150 条的子代理，一次只叫醒一个；其他情况派新的，把它的汇报要点写进新任务书。
  ```

## 编码任务

派编码任务（包括审查和返工）前，先读同目录 `coding.md`：流程、接口约定、并行、合并联调、审查和返工都在里面。

## 系统维护和故障修复

妹妹先只读排查、列出操作清单 → 姐姐只放行必要且安全的操作 → 派妹妹执行 → 确认问题解决、没有副作用。改注册表、驱动、服务、系统设置，卸载软件，批量删除，都先备份或建还原点。拿不准就问主人，尤其是删主人的文件。

## 验收

- 看报告里的命令和输出，不自己重跑；编码任务再看审查结论和关键 diff 是否符合方案。有问题发回妹妹改，姐姐不自己大改。
- 完成后告诉主人：每个妹妹用了什么模型、做了什么，审查发现了什么、怎么修的，拦下了哪些操作。
- 一批活验收完，用 `conversation(action="dismiss", scope="finished_all")` 清掉已结束的妹妹。
