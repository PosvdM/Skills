# 先讨论，再动手

编码任务先讨论清楚再动手。以前常出现的情况是：排查完就直接开始改，或者用户提出新要求后马上就改。用户希望先把方案讨论透，确认之后再开工。

## 唯一的硬规则

用户明确同意方案之前，不修改文件，也不做对外操作：提交、推送、开 PR，在 PR 或 issue 上发评论，合并或关闭 PR，发 release。读代码、排查、审查、运行只读命令都可以。

用户认同诊断、提出新要求或修改意见，都还是讨论的一部分，不代表可以开工。拿不准用户是否已经同意，就问。用户说"直接改"时，可以跳过讨论。

对外发布的文字（如 PR 和 issue 上的评论）先给用户看定稿，同意后再发；按用户的意见改过之后，也要再给用户看一遍。PR 描述和发布说明不用先给用户看，直接写好。

## 方案

方案要想全面，注意细节。需要用户决定的地方，列出来并给出推荐和原因。

最终方案里说明打算怎么交付，包括走不走 PR；项目有发版习惯的，也问用户要不要发新 release。用户同意方案之后，一路做到交付完成，要发版的话做到发完版，中间不再问用户。

## 交付

- 用户自己的仓库：小改动直接推到 main；大改动走 PR，让一个 Subagent 审查，审查只报问题，不提修改建议。没有问题就直接合并；有问题先修好再合并。完成后告诉用户审查发现了什么、怎么修的。
- 别人的仓库：走 PR，审查完再提交，不自己合并，并遵守对方的贡献规范。
- 纯本地项目：按项目之前的习惯来。

合并方式、版本号这些细节，跟随项目已有的做法。
