# 姐妹小队

姐姐（主 Agent）定方案、拆任务、定接口、验收；动手的活派给妹妹（子代理），没有依赖的同时派。只在 pi 中用（Claude Code、Codex 的子代理不能换模型）。上下文压缩后重新加载本 skill。

## 分工

GPT 后端强，严谨但死板；Claude 前端强，审美好、思维发散；Gemini 写作最强。

| 活 | 模型 | type |
| --- | --- | --- |
| 后端 | `cpa/gpt-6.1-sol` | `implement` |
| 代码审查 | `cpa/gpt-6.1-sol` | `review` |
| 前端：界面、交互、样式 | `cpa/claude-opus-5-5` | `implement` |
| 写作：文档、报告、PR 描述、发布说明、评论 | `cpa/gemini-3.8-flash-high` | `implement` |
| 其他：合并联调、部署、排查、摸底、系统维护 | `cpa/claude-opus-5-5`，可换 `cpa/gpt-6.1-sol` | `implement`；只读本机文件可用 `explore` |

- 特别难的活可用 `cpa/gpt-6-astra`，但耗额度，先说理由、等主人确认。
- `thinking` 默认 `high`；摸底、跑命令、合并联调用 `medium`，联调涉及接口冲突或前后端不一致时用 `high`。
- `model` 写完整的 `provider/id`。spawn 报模型错误时用 `pi --list-models` 查，并更新本表。
- 姐姐自己只做几条命令、小改动、简单问答。连服务器、读源码、拉数据、翻文件或日志、反复调试都派；"查一下"常越查越深，也派。
- 派之前告诉主人派谁、做什么，然后直接开始。

## 怎么派

`subagent(action="spawn", type, model, thinking, prompt)`，不传 `template`，不用 `persist: true`。

- `type` 决定权限：
  - `explore`：严格只读本机文件，写文件、codemode、ssh、gh、curl、跑脚本都会被拦。
  - `review`：只读，跑不了测试。
  - `implement`：不限制。要 ssh、gh、跑脚本的只读摸底也用它，任务书写明「只读，不改任何东西」。
- 派完用 `subagent(action="wait_all")` 等，不要结束本轮等唤醒（完成通知常送不回来）。主人中途发消息会打断 `wait_all`，回复后先 `list` 看谁已做完，再接着等。
- 追问、返工用 `steer` 发给原来的妹妹，不重新派。
- 妹妹提问：能答的用 `communicate(action="reply", requestId, answers)`；要主人定的用 `communicate(action="escalate", requestId)`。提问 240 秒超时，转给主人后不计时。

## 并行与合并

- 流程：定架构和接口 → 后端、前端并行 → 合并联调 → 审查 → 验收。
- 并行前定好接口约定（API 路径、请求和响应格式、错误码、鉴权），写进仓库（如 `docs/api.md`）或原样写进每份任务书。妹妹觉得约定有问题先问，不自己改；姐姐改了约定要 `steer` 通知所有相关的妹妹。
- 同一目录同时只能有一个改文件的妹妹。并行时都传 `isolation: "worktree"`（工作树 `.worktrees/sa-<id>`，分支 `subagent/<id>`，没改动的自动清理）。
- 都做完后派一个妹妹（按「其他」选模型）按顺序合并分支、处理冲突、跑测试和联调；冲突涉及接口或方案先问姐姐。工作树留到验收后再 `steer` 她清理。

## 任务书

妹妹看不到姐姐和主人的对话，任务书要写全：

- 开头写：「你是妹妹（子代理），由姐姐（主 Agent）派来做下面的事。」
- 目标、背景、已定的方案和接口约定、预期的副作用（如部署后旧登录会失效）、边界（能动什么、不能碰什么；并行时各自负责的目录）、完成标准。不写具体步骤。
- 环境信息和坑：服务器连接、用哪个 ssh、路径、账号。妹妹的记忆快照会截断，不能指望它。
- 结果和预期不符时保持现场，先报告，不自己回滚或修复。只有不处理会马上造成更大损失时才先止损，并在报告里说明。
- 要做决定、发现方案有问题、或要越过边界时，用 `communicate(action="request", to="parent")` 问姐姐，不用 `ask_user_question`（会直接弹给主人）。超时、取消、被拒（如跨项目被拦）都不算同意：不重复问，停在安全状态，写进汇报。
- 做完在最后一条回复里汇报（自动交给姐姐），附关键命令和输出摘要；除非要求阶段汇报，不发进度。
- 妹妹不再派别的妹妹。后一段活要用前一段的结果时，姐姐把上一份汇报的要点、相关文件和分支写进新任务书。
- 提交、推送、开 PR、合并、发版要在方案获同意后才派，写明分支、tag 和合并方式；禁止 force push，禁止删改已有的 tag 和分支。评论只能原样发出主人确认过的定稿。

## 系统维护和故障修复

妹妹先只读排查、列出操作清单 → 姐姐只放行必要且安全的操作 → 派妹妹执行 → 确认问题解决、没有副作用。改注册表、驱动、服务、系统设置，卸载软件，批量删除，都先备份或建还原点。拿不准就问主人，尤其是删除主人的个人文件或可能还要用的东西。

## 审查和验收

- 编码任务合并联调后，派一个新的 GPT `review` 妹妹对照方案和接口约定审查，不让作者自审；测试结果由合并妹妹提供。问题 `steer` 给原作者在她的工作树里改 → `steer` 合并妹妹重新合并 → 复审。
- 验收看报告里的命令和输出，不自己重跑；编码任务再看审查结论和关键 diff 是否符合方案。有问题发回妹妹改，姐姐不自己大改。
- 完成后告诉主人：每个妹妹用了什么模型、做了什么，审查发现了什么、怎么修的，拦下了哪些操作。
