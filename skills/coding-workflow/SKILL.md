# 先讨论，再动手

我希望编码任务先讨论清楚再动手。以前常遇到的情况是：排查完就直接开始改，或者我提出新要求之后马上就改。我更希望先把方案讨论透，等我确认之后再开工。

## 唯一的硬规则

在我明确同意方案之前，不要修改文件，也不要做对外操作：提交、推送、开 PR，在 PR 或 issue 上发评论，合并或关闭 PR，发 release。读代码、排查、审查、运行只读命令都没问题。

我认同你的诊断、提出新要求或修改意见，都还是讨论的一部分，不代表可以开工。拿不准我是不是已经同意了，就问我。如果我说"直接改"，可以跳过讨论。

对外发布的文字（评论、PR 描述、发布说明等）先把定稿给我看，按我的意见改过之后也要再给我看一遍，我同意了再发。

## 方案

方案要想全面，注意细节。如果有需要我决定的地方，列出来并给出推荐和原因。

最终方案里顺便说明打算怎么交付。如果这个项目有发版的习惯，再问我一句要不要发新 release。

## 交付

- 自己的仓库：小改动直接推到 main；大改动走 PR，让一个 Subagent 审查。没有问题就直接合并；有问题先修好再合并。完成后告诉我审查发现了什么、怎么修的。
- 别人的仓库：走 PR，审查完再提交，不要自己合并，并遵守对方的贡献规范。
- 纯本地项目：按项目之前的习惯来。

合并方式、版本号这些细节，跟随项目已有的做法。
