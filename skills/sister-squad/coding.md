# 编码任务

派编码任务（包括审查和返工）前读本文件。模型和 `type` 见 SKILL.md「分工」。

流程：定架构和接口 → 后端、前端并行 → 合并联调 → 审查 → 验收。

- 接口约定：并行前定好 API 路径、请求和响应格式、错误码、鉴权，写进仓库（如 `docs/api.md`）或写进每份任务书。妹妹觉得约定有问题先问，不自己改；姐姐改了约定要 `steer` 通知相关的妹妹。
- 并行：同一目录同时只能有一个改文件的妹妹，并行时都传 `isolation: "worktree"`（工作树 `.worktrees/sa-<id>`，分支 `subagent/<id>`）。
- 合并联调：都做完后派一个 Claude 妹妹按顺序合并分支、处理冲突、跑测试和联调；冲突涉及接口或方案先问姐姐。工作树留到验收后再 `steer` 她清理。
- 审查：派一个新的 GPT `review` 妹妹对照方案和接口约定审查，不让作者自审；测试结果由合并妹妹提供。把 diff 导出成文件给她并标出改动范围（她可能跑不了 git），相关代码她自己读。只报这次改动引入的问题；说会影响别处时，要指出是哪段代码、什么情况下出错。不报风格。范围外的问题单独列出，不算这次必须修的。只列问题和严重程度，不提建议。
- 第二审查：大 PR 或换机制后的第一轮，先查额度，用同一份任务书和 diff 另派 neon，允许她提建议、核对作者的取舍。姐姐逐条核对两边，只转很好的建议；她定级常偏低，不单凭她的结论合并。
- 返工：审查问题 `steer` 给原作者在她的工作树里改 → `steer` 合并妹妹重新合并 → 复审。
